# 社群活动整单退款

已实现小程序申请退款、Redis 防并发、唯一退款记录、通联线上退款/验签查询、Redis 延迟查询任务、后台退款列表与小区数据权限。

## 规则

- 本人已支付、未核销/未签到、未申请退款的有效订单可申请；不限制支付时间或场次开始/结束时间。退款中、已退款和未支付订单不可重复申请。
- 免费订单不进入退款流程，不支持部分退票；前端只传订单 ID。
- 金额根据原支付单计算并与报名订单核对。线上款原路退，平台余额在本地事务中退回并登记余额流水。
- 退款中保留名额，禁止核销；成功后订单状态改为 20，现有报名人数和库存统计实时扣除该订单。
- 不自动重新申请退款。超时、失败、待人工核对在用户端始终显示“退款中”。后台可以查询原退款状态，不能通过用户重复请求生成新单。
- 管理员不能取消存在有效报名、待支付或退款中订单的待开始活动，避免取消与支付并发；本功能不执行管理员自动退款。

## 当前运行方式

自动查单兜底暂时关闭：`config/social_activity_refund.php` 中 `auto_query_enabled=false`。无需新增 Supervisor 队列进程。退款接口明确成功仍直接完成本地退款；处理中、超时或响应异常保留“退款中”，不投递自动查询任务。已有旧队列任务被消费者取出时会直接删除，退款记录不会删除。

后台手动查询状态和已配置的回调入口继续保留；用户刷新页面只读取本地状态，不会触发通联查单。补偿查询命令保留供人工使用，目前无需配置定时任务。

以后恢复兜底时，将该开关改为 true，并按下面说明配置消费者；关闭期间未投递任务的待确认记录可通过补偿查询命令核对。

## 后台人工更新

退款列表支持退款状态和报名订单状态筛选。未完成的退款可点击“更新退款状态”，也可勾选当前页记录执行“批量更新退款状态”。批量操作由页面逐笔请求现有查询接口，需保持页面打开；每笔独立校验菜单/小区权限并使用 Redis 锁，一笔请求异常不影响后续。显示逐笔结果及成功、失败、待确认、请求异常数量。

通联确认成功才完成余额入账、取消票券和更新报名订单；确认失败保存退款失败状态及失败原因，用户端仍显示退款中。超时等查询异常不能判定为退款失败。已成功记录禁止选择，也不会再次查单或入账。本次无数据库结构变更。

## 安装与配置

先执行 `php tools/install_social_activity_refund.php`。脚本可重复执行，创建退款表、新增订单字段及社群活动下“退款列表”菜单。非超级管理员需在角色管理中分配新菜单；查询接口另外按管理员的小区范围限制数据。

原支付商户号、应用 ID、私钥与支付单号取自原支付记录，不使用当前活动的支付配置。新报名订单记录主办小区快照；历史订单缺少快照时安装脚本用当前活动补报表归属，该历史归属不能代表历史支付商户。

退款签名直接使用原支付单的商户号、AppID、私钥，无需新增支付设置项。以下是可选的回调和测试环境覆盖项：

```ini
[ALLINPAY]
REFUND_NOTIFY_URL = "https://你的接口域名/v20/public/index.php/social_activity/api.refundNotify/notify"
REFUND_TEST = false
```

通知地址不可带查询参数，HTTPS 使用 443。退款请求和查询均直连固定的通联 HTTPS 地址，验证服务器证书及主机名；退款接口返回 `retcode=SUCCESS` 且 `trxstatus=0000`，核对商户、退款单号及退款流水后立即按原申请金额完成本地退款，不额外查单；查询响应仍需核对金额。回调只触发查单，不直接采信其成功状态。

原支付单的 `platform_public_key` / `public_key`、系统 `allinpay_public_key` / `pay_allinpay_public_key` 如已配置则复用验签；旧的 `social_activity_refund.public_key` 保留兼容。没有独立公钥配置时仍可用原支付参数对接，不添加支付页面字段。

Web PHP 和队列 PHP 均需 Redis、openssl、curl、bcmath、mbstring、pdo_mysql 扩展。以下队列部署说明仅在恢复自动兜底后适用。保持系统现有 Redis 队列消费者运行；如没有消费者，启动 `php think queue:work --queue default --tries 0`。仅处理中、超时、响应不明确或本地入账异常的记录在申请后进入延迟查询队列；明确成功、明确失败及待人工处理不入队。首次延迟 20 秒，后续间隔 60 秒。任务只查询原退款单，不重发退款，持续未确认超过 24 小时转待人工处理。

补偿查询命令：`php think socialActivityRefundQuery`。可接入现有服务器定时任务；同样只查询待确认记录。后台“查询状态”可查询失败或待人工处理记录，查得成功后完成本地入账。不要直接修改退款表状态或删除唯一退款记录。

历史旧通联退款方法只是内部登记，历史已退款订单需单独对账；本次不会批量补退，也不修改其他业务的通联退款行为。

## 验证

`php tools/tests/social_activity_refund_policy_test.php` 验证订单资格、不受支付及场次时间限制、金额转换、RSA 签名、防篡改与商户匹配。

仅在测试环境运行：`php tools/tests/social_activity_refund_integration_test.php --allow-test-fixtures`。使用真实 Redis 锁和数据库事务，通联及入队均使用测试桩，所有用户、订单、退款、余额流水测试数据最终回滚。覆盖接口直接成功不查单不入队、处理中/超时/不完整响应入队、明确失败不入队、重复申请、旧锁释放、核销互斥、余额退款幂等、超时/失败、列表隔离与禁止取消已有报名的活动。

真实商户验收使用现有支付配置，验证真实退款、回调及查询；本地自动测试不发起真实资金交易。

## 用户端退款结果展示（更新）

申请响应、详情及订单列表按实际结果展示：成功为“已退款”，失败、待人工处理或已记录处理异常统一为“退款失败，请联系工作人员”，正常待确认才显示“退款中”。具体原因只提供给后台。该展示规则替代上文失败仍显示退款中的旧说明。展示失败不改变资金事实，订单仍锁定禁止重复退款或核销；工作人员查单确认成功后仍可完成退款。无需新增字段。
